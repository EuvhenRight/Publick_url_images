# AI-Generated Pull Request Trust Checklist

Use this checklist when an AI tool creates or substantially edits code. The goal is not to slow the team down; it is to make verification explicit so reviewers can trust the change faster.

## 1. Context

Before review, the author or AI assistant should answer:

- What problem is this PR solving?
- What files, services, APIs, or data models were touched?
- What assumptions did the AI make?
- What existing behavior must remain unchanged?
- Who owns the affected area?

## 2. Change Summary

Include a short summary in the PR description:

```md
## Summary
- Changed:
- Why:
- User-visible impact:
- Internal impact:

## AI involvement
- Generated by AI: yes/no/partial
- Human-reviewed before opening PR: yes/no
- Known uncertainties:
```

## 3. Risk Review

Ask whether the change affects any of these areas:

- Authentication or authorization
- Payments, billing, or pricing
- Data deletion, migration, or retention
- Personally identifiable information
- External API contracts
- Background jobs or queues
- Caching behavior
- Error handling or retries
- Performance-sensitive paths
- Observability, logging, or alerting

If any answer is yes, require a more detailed review plan.

## 4. Test Evidence

A trustworthy AI-generated PR should explain how it was tested.

Minimum evidence:

- Unit tests added or updated
- Existing test suite run successfully
- Manual verification steps documented
- Edge cases considered

Example:

```md
## Test plan
- Ran: npm test -- user-service
- Added tests for:
  - successful update
  - missing user
  - unauthorized caller
- Manually verified:
  - API returns 200 for valid request
  - API returns 403 for unauthorized request
```

## 5. Reviewer Questions

Reviewers should ask:

- Does the change solve the stated problem, or only appear to?
- Is the implementation consistent with existing patterns?
- Did the AI introduce unnecessary abstraction?
- Are there hidden changes outside the main intent?
- Are error states handled deliberately?
- Are tests meaningful, or do they only confirm the implementation?
- Would a future maintainer understand this change without the AI context?

## 6. Rollback Plan

Every AI-generated production change should have a clear path back.

Document:

- Whether the change can be reverted cleanly
- Whether a feature flag is involved
- Whether database changes are reversible
- Whether monitoring exists for failure signals

Example:

```md
## Rollback plan
- Safe to revert this PR directly: yes
- Feature flag: checkout_new_retry_logic
- Watch after deploy:
  - payment authorization error rate
  - checkout latency p95
  - retry queue depth
```

## 7. Final Gate

Do not merge until these are true:

- The author can explain the change without relying on the AI transcript
- The reviewer knows where to focus their attention
- Tests cover the risky behavior, not just the happy path
- The PR description includes context, test evidence, and rollback notes
- Any uncertainty is documented rather than hidden

## Simple Rule

AI can accelerate the first draft. The team still owns correctness, maintainability, and production impact.

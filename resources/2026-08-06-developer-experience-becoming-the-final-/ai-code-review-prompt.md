# Prompt: Review AI-Generated Code for Trust, Not Just Correctness

Use this prompt with an AI assistant when reviewing a pull request that was fully or partially generated by AI.

```text
You are reviewing a pull request that may contain AI-generated code.

Your job is not only to say whether the code works. Your job is to help a human reviewer decide whether the change is trustworthy enough to ship.

Review the diff using this structure:

1. Intent
- What does this PR appear to be trying to do?
- Is the implementation aligned with that intent?
- Are there changes that seem unrelated to the stated goal?

2. Risk Areas
Identify whether the change touches any of these:
- authentication or authorization
- data deletion, migration, or retention
- payments, billing, or pricing
- personally identifiable information
- public APIs or contracts
- background jobs, queues, or retries
- caching
- concurrency or async behavior
- performance-sensitive paths
- logging, metrics, or alerts

For each risk area, explain the specific file and line or function where the risk appears.

3. Correctness Review
Look for:
- logical errors
- missing edge cases
- invalid assumptions
- inconsistent error handling
- race conditions
- null, undefined, or empty-state problems
- behavior changes that are not documented

4. Test Review
Evaluate the tests. Answer:
- What behavior is covered?
- What important behavior is not covered?
- Are the tests asserting outcomes or merely implementation details?
- What additional tests would increase confidence?

5. Maintainability Review
Look for:
- unnecessary abstraction
- duplicated logic
- inconsistent naming or style
- code that does not match nearby patterns
- comments that explain what the code does but not why

6. Verification Plan
Create a practical checklist for the human reviewer:
- commands to run
- manual checks to perform
- logs, metrics, or dashboards to inspect after deploy
- rollback considerations

7. Final Recommendation
Return one of:
- Low risk: likely safe after normal review
- Medium risk: needs targeted changes or tests
- High risk: should not merge without deeper review

Be specific. Cite files, functions, and behaviors. Do not give generic advice.
```

## Optional Add-On: Ask for a Reviewer Map

If the PR is large, add this instruction:

```text
Create a reviewer map that lists each changed file, why it changed, who should review it, and what question that reviewer should answer.
```

Example output format:

```md
| File | Why it changed | Best reviewer | Key review question |
|---|---|---|---|
| src/auth/session.ts | Updates token refresh behavior | Auth owner | Can this create a stale or over-permissive session? |
| src/api/users.ts | Adds new response field | API owner | Does this change the public contract? |
```

## Optional Add-On: Ask for Missing Context

If the assistant sounds too confident, add:

```text
List the information you would need to be more certain. Separate confirmed facts from assumptions.
```

This helps prevent plausible but unsupported review comments.
